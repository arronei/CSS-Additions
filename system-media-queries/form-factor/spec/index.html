Abstract

This specification adds the form-factor media feature, which reports the kind of device the page is shown on, from a closed list: a desktop computer, a phone, a tablet, a television, a watch, a headset, an e-ink reader, or a car. Media queries already describe what a device can do, and a page can often guess from that, but the guesses are wrong in the cases that matter, and nothing distinguishes a television from a laptop. The feature matches the form factors of the User-Agent Client Hint of the same name, is limited in cross-origin frames by the same policy that delegates that hint, and falls back to the coarse mobile signal that every site already receives where fingerprinting protections apply.

1. Introduction

This section is non-normative.

A page on a television is read from across a room with a remote in hand. A page on a watch has a few seconds of the user’s attention. A page in a car must not ask for careful aim. A page on an e-ink reader shouldn’t animate. These are different designs, not different sizes.

[MEDIAQUERIES-5] describes what a device can do, and a page can guess the kind of device from that: a large viewport with a fine pointer is probably a computer, and slow suggests e-ink. The guesses are wrong exactly where it matters. A television reports a large viewport and looks like a desktop, though it is used from three meters away with a directional pad. A tablet and a touchscreen laptop report the same pointer and hover capabilities. A car’s screen reports nothing that distinguishes it from a tablet.

/* A television is read from across the room, and focused with a remote */
@media (form-factor: tv) {
  :root { font-size: 24px; }
  :focus-visible { outline: 4px solid; outline-offset: 4px; }
  .hover-only-toolbar { display: none; }
}

/* A watch shows one thing at a time */
@media (form-factor: watch) {
  .sidebar, .related, .footer-links { display: none; }
  .headline { font-size: 1.1rem; }
}

/* A car: bigger targets, less to read, nothing that moves */
@media (form-factor: automotive) {
  button, a.button { min-block-size: 4rem; font-size: 1.5rem; }
  .marquee { animation: none; }
}

/* E-ink: no animation, no gray-on-gray */
@media (form-factor: eink) {
  * { animation: none !important; transition: none !important; }
  body { color: black; background: white; }
}

The kinds of device are the ones that the Sec-CH-UA-Form-Factors client hint already defines [UA-CLIENT-HINTS], with one addition, tv, which that hint had and then dropped; see § 2.3 Televisions. Unlike the platform [PLATFORM-MEDIA-QUERY], this feature does reveal something that a site has to ask for today, so § 2.5 Frames and § 2.6 Reduced exposure limit who gets it.

2. The form-factor feature

Name: form-factor
For: @media
Value: desktop | mobile | tablet | tv | watch | xr | eink | automotive | other
Type: discrete

The form-factor media feature is a system media feature. A device can have more than one form factor: a watch is also mobile, and a car’s screen can also be a tablet. The feature matches a keyword when that keyword is one of the document’s form factors, rather than testing a single value.

The form factors of a document are the kinds of device it is shown on, each of which is:

desktop

A personal computer.

mobile

A small, touch-oriented device that the user carries with them.

tablet

A touch-oriented device larger than a mobile one, that isn’t typically carried on the person.

tv

A television or set-top device, shown on a distant screen and usually operated with a remote control.

watch

A device worn on the wrist, whose screen is typically less than two inches.

xr

An immersive device that augments or replaces the surroundings.

eink

A device with a screen that updates slowly and has limited or no color.

automotive

A device built into a vehicle, whose user may be driving it and unable to attend to small details.

other

A kind of device with no keyword here, or one the user agent chooses not to identify. A document whose form factors are empty or unknown has other as its only form factor.

In a boolean context, the feature is always true.

The list of keywords is closed. A user agent must report other for a kind of device with no keyword, and must not invent keywords. New keywords are added by revising this specification.

On a watch, both of these match, because the device’s form factors are watch and mobile: 
@media (form-factor: watch) { … }
@media (form-factor: mobile) { … }

A page that wants phones but not watches says so:

@media (form-factor: mobile) and (not (form-factor: watch)) { … }

2.1. Adding keywords

A keyword added in a later revision is an unknown value to a user agent that implements an earlier one, and a media query that evaluates to unknown because of it is replaced with not all [MEDIAQUERIES-4]. That includes a query that negates it, so not (form-factor: projector) would match nothing in such a user agent.

A new keyword is safest in its own media query in a comma-separated list, where only that query is dropped: 
@media (form-factor: tv), (form-factor: projector) { … }

A page can’t test for a keyword with @supports, but script can: matchMedia("(form-factor: projector), not all and (form-factor: projector)").matches is true when the user agent knows the keyword, and false when it doesn’t, including when it doesn’t support form-factor at all. Keeping the list closed means that each new keyword arrives through a revision that authors can track, rather than differing between user agents indefinitely.

2.2. Where the value comes from

A user agent that implements [UA-CLIENT-HINTS] must report the same form factors that it reports in Sec-CH-UA-Form-Factors and in navigator.userAgentData.getHighEntropyValues(["formFactors"]) for the document, lowercased, plus tv where § 2.3 Televisions applies.

A user agent that doesn’t implement those must report the kinds of device that match the definitions above, except that its form factors must agree with the platform it presents [PLATFORM-MEDIA-QUERY], and this takes precedence over the definitions: if the user agent presents itself as a desktop system, as browsers do in a "request desktop site" mode, the document’s form factors are desktop, plus tv where § 2.3 Televisions applies.

A user agent that implements the client hint already applies its own presentation to the hint, so the first rule covers it.
At the time of writing, Safari on iPads other than iPad mini presents itself as macOS by default [WEBKIT-SAFARI-13], so those iPads report desktop rather than tablet. Chrome on Android doesn’t set the mobile bit on tablet-sized screens, so its client hint reports "Desktop" there [CHROMIUM-UA-UTILS], and on premium tablets it also presents itself as Linux by default [CHROME-DESKTOP-MODE]; those tablets report desktop too.
The feature can only be as detailed as the user agent’s own classification, and today that is coarse. Only Chromium implements Sec-CH-UA-Form-Factors, and by default it reports "Mobile" or "Desktop" from the mobile bit, adding "XR" on Android XR devices [CHROMIUM-UA-UTILS]. Chromium’s own browser reports "Tablet" only in ChromeOS’s "request tablet site" mode (Android apps that embed its WebView can set any value), and no default code path reports "Automotive", "EInk", or "Watch". Together with the desktop presentation of most tablets, this means tablet would match almost nowhere in current browsers. The keywords are worth defining anyway, so that a user agent that does classify devices has one way to say so, but authors should expect mobile and desktop to be most of what they see.

2.3. Televisions

Sec-CH-UA-Form-Factors has no value for a television, so a television browser that implements it reports something else; one built on Chromium reports "Mobile" or "Desktop" from the same mobile bit as any other device, unless its maker changes that [CHROMIUM-UA-UTILS]. A user agent must report tv for a television or set-top device even so.

This is the one place where the feature and the client hint can disagree, and it should be fixed in the hint rather than here. The hint had a television value: when it was first added, in March 2023, its values were "Automobile", "Mobile", "Tablet", "TV", "VR", "XR", and "Unknown" [UA-CH-338], and the W3C Media and Entertainment Interest Group’s issue on how television browsers should identify themselves was updated to note that the new hint allowed "TV" [ME-IG-47]. In the discussion that followed, "TV" was dropped "in the absence of use-cases for it identified so far in this conversation" [UA-CH-344], and in September 2023 the hint became a list without it [UA-CH-343].

The hint’s own criteria for adding a value are "a new form-factor that users interact with in a meaningfully different way; a compelling use-case where sites would like to change how they interact with users on that device; and no reliable way to identify that new form-factor using existing hints" [UA-CLIENT-HINTS]. A television meets all three: it is used from across a room with a remote control, § 1 Introduction gives the use case, and no client hint identifies it. Among media features, only none hints at it, and not on televisions whose remotes act as pointers. Otherwise, television browsers can often be recognized only from unstandardized User-Agent tokens. See § 6 Open issues.

2.4. Changes

The value is determined when the document is created, and doesn’t change while the document exists.

2.5. Frames

The feature uses frame-scoped exposure [MEDIA-FEATURE-PRIVACY]. Its policy-controlled feature is "ch-ua-form-factors", the one that already delegates the client hint [CLIENT-HINTS-INFRASTRUCTURE], whose default allowlist is 'self'.

In a document that isn’t allowed to use it, the feature takes its restricted value, which is the coarse form factor.

A site that delegates the client hint to a frame, so that the frame’s server can adapt, gives the frame’s style sheets the same information: Permissions-Policy: ch-ua-form-factors=(self "widgets.example").

2.6. Reduced exposure

The feature is under user control. In a reduced-exposure context, and when the user turns the feature off, it is the coarse form factor.

The coarse form factor of a document is mobile if the user agent reports itself as mobile, in the Sec-CH-UA-Mobile client hint, in navigator.userAgentData.mobile, or with a "Mobile" token in its User-Agent header, and desktop otherwise.

The coarse form factor is the bit that every site already receives on every request, so a document that gets only it learns nothing new. A watch or a car falls back to mobile, and a television to desktop, which is what a page assumes today.

3. Privacy considerations

3.1. What the feature reveals

The feature reveals which kinds of device, from a closed list of nine, the page is being shown on. It doesn’t reveal the device’s model, manufacturer, screen size, operating system version, or price.

Unlike the platform [PLATFORM-MEDIA-QUERY], this is more than every site receives today. Of the signals it corresponds to, only the mobile bit is sent to every site by default; the rest of Sec-CH-UA-Form-Factors is a hint a site must ask for, and which isn’t shared with cross-origin frames unless the top-level site delegates it. This specification keeps both of those limits: § 2.5 Frames uses the same policy, and § 2.6 Reduced exposure falls back to the mobile bit.

3.2. Fingerprinting

Most users are on a phone, a tablet, or a computer, so for most users the feature reveals little more than the mobile bit does. The users it identifies are the ones on uncommon devices: a watch, a headset, an e-ink reader, or a car. If one user in a thousand browses from a watch, the feature tells a site about 10 bits about that user.

Two things limit the cost:

  • Some of those devices are already recognizable without this feature: a watch has a tiny viewport and often round safe-area insets, and an e-ink reader reports slow and often 0. For those, the feature mostly saves authors from guessing. A headset would be recognizable from environment-blending, but no browser implements that feature yet, and a car has no such signal, so for users of those devices this feature does reveal something new.

  • The list is closed, so an unusual device reports other rather than naming itself, and the value is restricted in frames and in reduced-exposure contexts.

The value never changes while a document exists, so it can’t link two documents by the moment it changed.

3.3. Embedded content

Cross-origin frames get the coarse form factor unless the embedding page delegates ch-ua-form-factors to them, which is exactly the rule the client hint already follows. A tracker embedded across many sites therefore learns the same bit it already gets from the User-Agent header.

3.4. Sensitive inferences

A device can suggest things about its owner. A car’s browser says the user is in a vehicle; a headset says they are wearing one; an e-ink reader or a watch suggests what someone bought. None of this is precise, and none of it approaches what the same page learns from its own content and the user’s IP address, but a site can use the value to decide who is worth serving: to charge differently, or to send an unusable page to devices its author didn’t like. See § 4.2 Refusing to serve devices.

3.5. Remaining risks

  • A user on an uncommon device is identified by the value in any document the value reaches, which is the top-level document and frames that the site delegates to.

  • The fallback for reduced-exposure contexts is a real loss of function for those same users: a watch in a private window gets the phone layout.

4. Security considerations

4.1. It is not feature detection

The kind of device doesn’t say which features work, how large the viewport is, or whether there is a pointer. Pages should keep using pointer, hover, update, overflow-block, environment-blending, the viewport features, and @supports for those, and use this feature for the things they can’t express: how far away the screen is, how much attention the user can spare, and what kind of control the user holds.

4.2. Refusing to serve devices

The clearest misuse is a page that decides some devices don’t deserve content: a site that shows a television or an e-ink reader a "please use a supported device" message rather than a page that works. This has a long history with user agent sniffing, and it is the reason CSS deprecated its device-class media types. Authors should treat the feature as a way to adapt, never as a way to exclude, and the fallbacks in this specification are designed so that an unrecognized device gets a usable layout rather than nothing.

4.3. Cars

automotive exists so a page can be safer to use while driving: larger targets, less text, no animation. A page could do the opposite. Nothing in CSS can prevent that, and vehicle systems restrict what browsers may show while moving; this feature doesn’t change those restrictions, and must not be treated as permission to show anything.

4.4. Not an input to decisions that matter

The user controls the value: desktop mode changes it, and so does turning the feature off. Pages must not use it for entitlement, fraud scoring, or any security decision.

5. Alternate proposals

5.1. Only capability features

CSS could keep describing capabilities and let pages infer the rest, adding features for the qualities that are missing, such as viewing distance or the kind of control the user holds. That is how the CSS Working Group has handled similar requests, turning "what device is this" into "what does it do", as the Device Posture API did by exposing folded rather than a device model [DEVICE-POSTURE]. The Working Group has open issues in this direction, for enclosed screens [CSSWG-9701] and for typical viewing distance [CSSWG-13398]. When the Working Group was asked to expose whether a device is mobile [CSSWG-7696], Tab Atkins, an editor of Media Queries, answered that the media types were deprecated and not reproduced as a media query "precisely because it’s an incoherent concept and never what you actually want". That issue is still open.

It was not chosen because the missing qualities are many and correlated, and because a user agent is better placed to classify its device than a page is, which is why Sec-CH-UA-Form-Factors exists. That argument is weaker than it looks: only Chromium implements the hint, and it classifies little beyond mobile and desktop (§ 2.2 Where the value comes from). A reviewer may well prefer this direction, and § 6 Open issues asks the question.

5.2. Reviving the media types

CSS had @media tv, @media handheld, and @media projection, and deprecated them, because media types "have proven insufficient as a way of discriminating between devices with different styling needs" [MEDIAQUERIES-4]; user agents must now make them match nothing. Media Queries explains that categories such as screen and handheld blended over time, and that media types were mutually exclusive, so a device could be only one of them. Authors also used them for layout, which viewport queries do better. This is the first objection this feature will meet. The feature is narrower: a device can have several form factors, capabilities and sizes are left to the features that describe them, and the rules keep an unrecognized device working.

5.3. Physical screen size

A feature for the physical size of the display would separate a television from a laptop, and a watch from a phone. It was not chosen because it is a continuous value, and therefore a much larger fingerprinting surface than a closed list of nine keywords, and because form-factor answers the question that authors actually ask.

5.4. Leaving it to the client hint

Sites can already request Sec-CH-UA-Form-Factors, which Chrome has supported since version 124, and serve different CSS. That works only in Chromium-based browsers, only for pages built on a server that varies its response, doesn’t work for static files, caches badly, and doesn’t work at all where script and server negotiation aren’t available, such as an HTML email or a document opened from disk.

6. Open issues

tv has no matching value in Sec-CH-UA-Form-Factors, so this specification requires a value the client hint can’t express. The right fix is to add "TV" back to the hint, which dropped it because no one in that discussion had identified a use case for it (§ 2.3 Televisions). Until then, should the feature report tv at all, or wait?

Should tablet exist? Safari on most iPads presents itself as a desktop computer by default, Chrome’s client hint reports "Desktop" on Android tablets, and Chromium’s own browser reports "Tablet" only in one ChromeOS mode (§ 2.2 Where the value comes from), so the keyword would match almost nowhere today. Keeping it costs little, and removing it would leave no way to say "tablet" if user agents start reporting it.

The CSS Working Group has already been asked for a "mobileness" media query, and participants including a Media Queries editor pushed back in that issue, which is still open [CSSWG-7696]. Does a closed list of device classes answer that objection, or should this proposal become the capability features that issue and [CSSWG-13398] point toward?

Should eink exist when update already reports slow? They aren’t the same thing, since a slow-updating LCD isn’t e-ink, but they overlap more than the other values do.

Is matching against a set the right model for a discrete media feature? Every other discrete feature in [MEDIAQUERIES-5] has one value at a time, and a set makes (form-factor: mobile) true on a watch, which some authors will not expect.

Should the restricted value in frames be the coarse form factor, or should a frame see nothing at all? The coarse value is what the frame’s own requests already carry, but it also means a frame always gets an answer that looks authoritative.

Appendix: Security and privacy questionnaire

This section is non-normative. These are the answers to the questions in [SECURITY-PRIVACY-QUESTIONNAIRE].

What information does this feature expose, and for what purposes?

Which kinds of device, from a closed list of nine, the page is shown on, so pages can adapt their design to the device rather than guess from its capabilities.

Do features in your specification expose the minimum amount of information necessary?

Yes. A closed list, with no model, size, or version, limited in frames and reduced to the mobile bit where fingerprinting protections apply.

Do the features expose personal information, PII, or information derived from either?

The kind of device can suggest what someone owns or that they are in a vehicle. See § 3.4 Sensitive inferences.

How do the features deal with sensitive information?

The same limits as the client hint it mirrors, plus a fallback to the bit every site already receives.

Does data exposed carry related but distinct information that may not be obvious to users?

Yes: owning a watch, a headset, or an e-ink reader, and being in a car.

Do the features introduce state that persists across browsing sessions?

No.

Do the features expose information about the underlying platform to origins?

Yes, the device class, which user agents that implement Sec-CH-UA-Form-Factors already compute for that hint.

Does this specification allow an origin to send data to the underlying platform?

No.

Do features enable access to device sensors?

No.

Do features enable new script execution or loading mechanisms?

No.

Do features allow an origin to access other devices?

No.

Do features allow an origin some measure of control over a user agent’s native UI?

No.

What temporary identifiers do the features create or expose to the web?

None. The value doesn’t change while a document exists.

How does this specification distinguish between behavior in first-party and third-party contexts?

Cross-origin frames get the coarse form factor unless the embedding page delegates ch-ua-form-factors, the same rule the client hint follows.

How do the features work in the context of a browser’s Private Browsing or Incognito mode?

Modes that protect against fingerprinting are reduced-exposure contexts, where the feature is the coarse form factor.

Does this specification have both "Security Considerations" and "Privacy Considerations" sections?

Yes.

Do features enable origins to downgrade default security protections?

No.

What happens when a document that uses your feature is kept alive in BFCache?

It keeps the value it was created with.

What happens when a document that uses your feature gets disconnected?

Nothing is kept.

Does your spec define when and how new kinds of errors should be raised?

No.

Does your feature allow sites to learn about the user’s use of assistive technology?

No. A device used as an accessibility aid, such as a switch-controlled tablet, reports the same value as any other tablet.

What should this questionnaire have asked?

Whether a feature lets a site decide that some users' devices aren’t worth serving.

Conformance

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with class="note", like this:

Note, this is an informative note.

tv has no matching value in Sec-CH-UA-Form-Factors, so this specification requires a value the client hint can’t express. The right fix is to add "TV" back to the hint, which dropped it because no one in that discussion had identified a use case for it (§ 2.3 Televisions). Until then, should the feature report tv at all, or wait? ↵
Should tablet exist? Safari on most iPads presents itself as a desktop computer by default, Chrome’s client hint reports "Desktop" on Android tablets, and Chromium’s own browser reports "Tablet" only in one ChromeOS mode (§ 2.2 Where the value comes from), so the keyword would match almost nowhere today. Keeping it costs little, and removing it would leave no way to say "tablet" if user agents start reporting it. ↵
The CSS Working Group has already been asked for a "mobileness" media query, and participants including a Media Queries editor pushed back in that issue, which is still open [CSSWG-7696]. Does a closed list of device classes answer that objection, or should this proposal become the capability features that issue and [CSSWG-13398] point toward? ↵
Should eink exist when update already reports slow? They aren’t the same thing, since a slow-updating LCD isn’t e-ink, but they overlap more than the other values do. ↵
Is matching against a set the right model for a discrete media feature? Every other discrete feature in [MEDIAQUERIES-5] has one value at a time, and a set makes (form-factor: mobile) true on a watch, which some authors will not expect. ↵
Should the restricted value in frames be the coarse form factor, or should a frame see nothing at all? The coarse value is what the frame’s own requests already carry, but it also means a frame always gets an answer that looks authoritative. ↵
