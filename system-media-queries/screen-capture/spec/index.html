Abstract

This specification adds the screen-capture media feature, which lets a page hide account balances, messages, and other personal details while the user is sharing or recording their screen. It is a protected media feature: the page’s appearance changes, in both the capture and on the user’s own screen, but the page can’t find out that a capture is happening. Script, layout, and the network see no difference, so the feature can’t be used to detect that the user is in a meeting, and a page can’t show the people watching anything the user doesn’t see.

1. Introduction

This section is non-normative.

People share their screens in meetings, record tutorials, stream games, and show support staff what went wrong. When they do, the page they share shows everything it shows them: the balance of their bank account, the preview of a private message, a notification badge, an API key. Native apps on some platforms can hide such things while the screen is recorded. Web pages can’t.

This specification lets a page do the same:

@media (screen-capture: active) {
  .balance, .message-preview, .api-key {
    color: transparent;
    text-shadow: 0 0 0.6em rgb(0 0 0 / 0.6);
  }
  .notification-count { background-color: transparent; color: transparent; }
}

Telling a page that the screen is being captured would also tell it that the user is in a meeting, or streaming, or talking to support, and would let a page look different to the people watching than it does when nobody is. So the feature is a protected media feature [MEDIA-FEATURE-PRIVACY]: rules that depend on it can change only colors, shadows, outlines, and decorations, and nothing the page can measure changes. Script that asks gets none.

Hiding images works with an overlay that is always there and is transparent until a capture starts: 
.avatar { position: relative; }
.avatar::after {
  content: ""; position: absolute; inset: 0; pointer-events: none;
  background-color: transparent;
}
@media (screen-capture: active) {
  .avatar::after { background-color: #9ca3af; }
}

2. The screen-capture feature

Name: screen-capture
For: @media
Value: none | active
Type: discrete

The screen-capture media feature is a protected media feature whose observable value is none. Every document uses protected evaluation for it.

Its actual value in a document d is:

active

d is being captured.

none

Otherwise. This value evaluates to false in a boolean context.

Because of protected evaluation, a rule under active can only change the paint-only properties, such as color, background-color, box-shadow, and outline. Its other declarations, such as display: none, have no effect. matchMedia("(screen-capture: active)") never matches, and no change event is ever fired for it.

2.1. Being captured

A document d is being captured when d’s visibility state is "visible", and the user agent knows that the part of the screen where d is displayed is included in one of these:

  1. A capture that the user agent makes, of a tab, window, or screen, for getDisplayMedia() or for its own casting or recording features.

  2. A screen recording or screen sharing session that the operating system reports to the user agent.

  3. A mirror of the display on another display, if the operating system reports it.

These are not captures, and must not make any document be captured:

  • Assistive technology, such as screen readers, screen magnifiers, and tools that read text from the screen or caption it.

  • The user agent’s own use of page images, such as tab thumbnails and previews.

  • A single screenshot.

The user agent should let the user exclude particular capture sessions, or particular apps that capture the screen, and should not count a remote desktop session in which the remote display is the only place the user sees the document.

Platforms report different things. Android 15 tells apps when their windows appear in a screen recording [ANDROID-SCREEN-RECORDING]. iOS and iPadOS report when the screen is being recorded, mirrored, or sent to another display. Desktop operating systems don’t generally tell apps that another app is capturing the screen, so on desktop computers the feature mostly reflects captures made by the user agent, such as sharing a tab or window into a video meeting in the same browser.

2.2. Timing

When a capture made by the user agent starts, the user agent must not include a frame showing a document in the capture until it has painted that document with its new painted style. When the operating system reports a capture that has already started, the user agent must paint the new painted style as soon as it can.

When a capture ends, the user agent should paint the new painted style at the next rendering opportunity.

2.3. The same picture for everyone

The user agent must show the user the same painted content that it includes in a capture. It must not paint a document one way for the user’s screen and another way for a capture.

This rule is what stops a page from showing the people watching something different from what the user sees. See § 4.2 Looking different to the people watching.

2.4. User control

The feature is under user control. When the user turns it off, the actual value is none in every document. The user agent must also let the user turn the feature off for a single capture session, while it is running, for example with a control in its sharing indicator.

The user agent should tell the user, while a capture is running, when a document in the capture is painted differently because of this feature, for example with a message in its sharing indicator such as "Some content on this page is hidden while you share".

User agents know when this happens: it is when a document’s painted style differs from its observable style because of this feature. Telling the user doesn’t tell the page anything.

3. Privacy considerations

3.1. What a capture reveals

If a page could find out that the user’s screen is being captured, it would learn:

  • What the user is doing. They are in a meeting, presenting, streaming, recording a tutorial, or getting help.

  • Who else can see. Someone else is watching the screen, now or later.

  • When. The moments a capture starts and stops are the same in every document on the screen, so a tracker present in two of them could link them.

Pages could use that to target streamers, to change what they show when a support agent is watching, or to record when the user is in meetings.

3.2. Why the feature is always protected

Every use of the feature is to hide something visual, and hiding something visual doesn’t need the page to know. The feature is therefore always evaluated with protected evaluation, with no way for a page to ask for more:

Channel What a page sees during a capture
Script matchMedia() reports none; computed styles are unchanged
Layout No box changes size or position, because only paint-only properties change
Network No resource is fetched or not fetched because of the capture
Timing No events are fired, no transitions run, and no performance entries are created
Embedded content A frame can hide its own content, and learns no more than the top-level document does, which is nothing

Because nothing is revealed, the feature needs no delay, no restriction in frames, and no special behavior in private browsing modes, and it can take effect before the first frame of the capture.

3.3. Fingerprinting and linking visits

The feature adds no information to a fingerprint and no moment that could link visits, because no document can observe its value.

3.4. Remaining risks

  • Interaction. A page could paint a message such as "click here" only during a capture, and learn that a capture is happening if someone clicks. This needs the user, or a viewer, to act on it.

  • The page’s own capture. If the user lets a page capture its own tab, the page sees the painted result. It already knows a capture is happening, because it started it.

  • Viewers. The people watching can see that some content is hidden. That tells them the page hides content, not what it is.

4. Security considerations

4.1. Not a way to protect content

The feature reduces accidental exposure. It isn’t a security boundary, and it isn’t a way to protect content from copying:

  • The user agent only knows about some captures. Most desktop operating systems don’t report captures by other apps.

  • Screenshots aren’t reported.

  • A camera pointed at the screen isn’t reported.

  • The user can turn the feature off.

Pages must not rely on the feature to keep anything secret.

4.2. Looking different to the people watching

A page could hide content during captures to avoid being seen by the people who would catch it: a fraudulent payment request hidden from a family member watching over a screen share, a scam hidden from a bank’s fraud team, or abusive content hidden from a victim trying to record it.

§ 2.3 The same picture for everyone means the page can’t show the user one thing and the viewers another. What the viewers see is what the user sees. A page can still change what both see while a capture is running, and the user could record the page without the hidden content. To prevent that from being used to hide evidence:

  • The user can turn the feature off for a capture session while it runs, and the capture then shows the page as it looks without a capture.

  • The user agent tells the user when content is hidden, so the user and the viewers know that what they see isn’t the whole page.

4.3. Screenshots

Screenshots are excluded because a page can’t hide anything before a screenshot is taken. Reporting them would only let pages detect screenshots, which could be used to punish users for keeping records.

4.4. Captures started by other pages

A page that asks the user to share another tab can make that tab hide its content, but only in the capture the page itself receives. It learns nothing about the other tab it wouldn’t see in the capture anyway.

5. Alternate proposals

5.1. An ordinary media feature

An ordinary media feature would let pages use any CSS, and script, during captures, such as switching to a larger layout for presenting. It was not chosen because it would reveal what § 3.1 What a capture reveals describes, and every case it adds beyond hiding content changes what the page shows the viewers rather than protecting the user.

5.2. Hiding content in the capture only

A property such as capture-visibility: hidden could hide an element in captures while the user still sees it on their screen, which is more convenient for the user. It was not chosen for two reasons. It would let a page show the viewers something different from what the user sees, which is what makes fraud during screen sharing work. And it could only apply to captures the user agent makes, because an operating system captures the pixels on the screen. Some operating systems can exclude a whole window from captures, but not part of one.

5.3. A capture event for script

Android 15 tells apps when their windows are recorded. A similar event for script would have the same problems as an ordinary media feature, and pages don’t need it to hide content.

5.4. Including screenshots

See § 4.3 Screenshots.

6. Open issues

Should a display mirrored to a projector count? Presenters would benefit, and the operating system usually knows, but mirroring isn’t always to an audience.

opacity and 'filter: blur()' are the most natural ways to hide content, and they aren’t paint-only properties. See the open issue in [MEDIA-FEATURE-PRIVACY].

Should operating systems be asked to report captures to apps, as Android 15 does, so that the feature works for desktop video meeting apps?

Appendix: Security and privacy questionnaire

This section is non-normative. These are the answers to the questions in [SECURITY-PRIVACY-QUESTIONNAIRE].

What information does this feature expose, and for what purposes?

None to the page. It lets the page’s appearance change during a screen capture, so the page can hide personal details.

Do features in your specification expose the minimum amount of information necessary?

Yes. The page can’t observe the value.

Do the features expose personal information, PII, or information derived from either?

No.

How do the features deal with sensitive information?

They help pages hide it during captures, without revealing that a capture is happening.

Does data exposed carry related but distinct information that may not be obvious to users?

No data is exposed. See § 3.4 Remaining risks for what a page can learn with the user’s help.

Do the features introduce state that persists across browsing sessions?

No.

Do the features expose information about the underlying platform to origins?

No.

Does this specification allow an origin to send data to the underlying platform?

No.

Do features enable access to device sensors?

No.

Do features enable new script execution or loading mechanisms?

No. Rules under the feature can’t load resources.

Do features allow an origin to access other devices?

No.

Do features allow an origin some measure of control over a user agent’s native UI?

No. The user agent’s sharing indicator may say that content is hidden; the page doesn’t control it.

What temporary identifiers do the features create or expose to the web?

None.

How does this specification distinguish between behavior in first-party and third-party contexts?

It doesn’t need to, because no context can observe the value.

How do the features work in the context of a browser’s Private Browsing or Incognito mode?

The same as in normal browsing.

Does this specification have both "Security Considerations" and "Privacy Considerations" sections?

Yes.

Do features enable origins to downgrade default security protections?

No.

What happens when a document that uses your feature is kept alive in BFCache?

It isn’t visible, so it isn’t being captured. When it is restored, it is painted for the current state.

What happens when a document that uses your feature gets disconnected?

Nothing is kept.

Does your spec define when and how new kinds of errors should be raised?

No.

Does your feature allow sites to learn about the user’s use of assistive technology?

No. Assistive technology doesn’t count as a capture.

What should this questionnaire have asked?

Whether a feature can make a page look different to people other than the user, and whether the user can tell.
