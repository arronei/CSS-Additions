Abstract

This specification adds the platform media feature, which reports the family of the user’s operating system from a closed list of keywords, so that a style sheet can follow that platform’s conventions: writing a shortcut as ⌘K or Ctrl+K, ordering the buttons of a dialog, offering the right download, or showing the right app store badge. The value must be the same platform the user agent already reveals in its User-Agent header and, where it has them, its client hints, including when the user agent deliberately reports a platform it isn’t running on, so the feature adds no information to any context. It never reports the version of the operating system, the device model, the architecture, or the browser.

1. Introduction

This section is non-normative.

Every operating system has conventions that its users know without being taught. On macOS the shortcut is ⌘K and the accept button of a dialog is on the right; on Windows the same shortcut is Ctrl+K and the accept button is on the left. An app downloads as a .dmg, an .exe, or a .deb. The share icon is a box with an arrow on iOS and three connected dots on Android, and the app store badge is a different image on each platform.

Media queries can describe what the device can do, but not whose conventions to follow. coarse doesn’t mean iOS: a Windows laptop with a touchscreen and an iPad both report it, and they want opposite button orders and opposite shortcut labels. Feature queries can’t help either, because the question isn’t whether the engine supports something, it’s what the user’s platform calls it and expects it to look like.

So pages work around it. They detect the platform once in script and write a class onto the root element, which is what Visual Studio Code does, and what user agent parsing libraries such as bowser and ua-parser-js exist to feed. Firefox needed the same thing for its own interface, and added a -moz-platform media feature in Firefox 99 [MOZ-PLATFORM] that only its own style sheets can use.

This specification gives style sheets the same thing, in a form that reveals nothing that the user agent doesn’t already send to every server in its User-Agent header.

/* Shortcut labels */
.key-mod::after { content: "Ctrl"; }
@media (platform: macos), (platform: ios) {
  .key-mod::after { content: "⌘"; }
}

/* Dialog buttons: accept last on Apple platforms, first on Windows */
.dialog-buttons { display: flex; }
@media (platform: windows) {
  .dialog-buttons .accept { order: -1; }
}

/* The right download, and the right store badge */
.download-dmg, .download-deb, .badge-app-store, .badge-play { display: none; }
@media (platform: macos) { .download-exe { display: none; } .download-dmg { display: inline; } }
@media (platform: linux) { .download-exe { display: none; } .download-deb { display: inline; } }
@media (platform: ios) { .download-exe { display: none; } .badge-app-store { display: inline; } }
@media (platform: android) { .download-exe { display: none; } .badge-play { display: inline; } }

The feature reports a family, never a version, and never a device. It is deliberately not a way to ask what the browser can do: that is what feature queries are for, and § 4.1 It is not feature detection explains why using it that way breaks browsers.

2. The platform feature

Name: platform
For: @media
Value: windows | macos | ios | android | linux | chromeos | other
Type: discrete

The platform media feature is a system media feature. Its actual value is the keyword for the document’s reported platform:

windows

Microsoft Windows.

macos

Apple macOS.

ios

Apple iOS and iPadOS.

android

Android, including systems built on it whose conventions are Android’s.

linux

A Linux or Unix-like desktop system that isn’t one of the above.

chromeos

ChromeOS.

other

Any other platform, and any platform the user agent chooses not to identify.

In a boolean context, the feature is always true.

The list of keywords is closed. A user agent must report other for a platform that has no keyword, and must not invent keywords. New keywords are added by revising this specification.

A closed list keeps the feature from identifying the users of uncommon systems. If every system had its own keyword, the few users of one would be easy to recognize, while the feature is worth little to them, because an author can’t design for a platform they have never seen. See § 3.4 The closed list.

2.1. Adding keywords

A keyword added in a later revision is an unknown value to a user agent that implements an earlier one, and a media query that evaluates to unknown because of it is replaced with not all [MEDIAQUERIES-4]. The negation of an unknown value is also unknown, so both of these match nothing in such a user agent, on any platform:

@media (platform: harmonyos) { … }
@media not (platform: harmonyos) { … }
A new keyword is safest in its own media query in a comma-separated list, because only the query that evaluates to unknown is dropped, with the default styles outside any query. 
.store-badge { display: none; }
@media (platform: android), (platform: harmonyos) {
  .store-badge { display: inline; }
}

In a user agent that knows android but not harmonyos, the rule still applies on Android.

A page can’t test for a keyword with @supports, which doesn’t accept media queries. Script can: matchMedia("(platform: harmonyos), not all and (platform: harmonyos)").matches is true when the user agent knows the keyword, and false when it doesn’t, including when it doesn’t support platform at all.

2.2. The reported platform

The reported platform of a document is the platform that the user agent presents to that document’s origin elsewhere. It is not necessarily the platform the user agent is running on.

A user agent must determine the reported platform as follows:

  1. If the user agent implements navigator.userAgentData [UA-CLIENT-HINTS], the reported platform is the value its platform property has, or would have if the document were a secure context, mapped with the table below.

  2. Otherwise, the reported platform is the platform identified by the User-Agent header the user agent would send with a request for the document.

navigator.userAgentData.platform platform
"Android" android
"Chrome OS", "Chromium OS" chromeos
"iOS" ios
"Linux" linux
"macOS" macos
"Windows" windows
Any other value, including "Unknown", "Fuchsia", and "OpenHarmony" other

The feature must agree with what the user agent reports elsewhere, even when that isn’t the platform it is running on. In particular:

  • If the user agent presents itself as another platform, as browsers do in a "request desktop site" mode and some do by default, the feature reports that other platform.

  • If the user agent normalizes or hides the platform to protect the user from fingerprinting, the feature reports the normalized platform, and reports other if the user agent identifies no platform.

At the time of writing:

  • Safari on iPad, other than iPad mini, sends the same User-Agent string as Safari on a Mac by default [WEBKIT-SAFARI-13], so the feature is macos. In 2019, WebKit said that a page loaded while Safari took up a third of the screen in multitasking got an iOS User-Agent string instead; a document loaded that way would report ios.

  • Chrome on iPad presents itself as iOS, with an iPad token, unless the user requests the desktop site, when it presents itself as macOS [CHROMIUM-IOS-UA]. The same iPad can therefore report macos in Safari and ios in Chrome.

  • Chrome on Android presents itself as Linux in desktop mode, which it turns on by default on premium tablets [CHROME-DESKTOP-MODE], so the feature is linux there.

This rule is what makes the feature safe: it follows the platform that the user agent already reports in navigator.userAgentData.platform or, without that, in its User-Agent header, including the user’s choice of desktop mode, so it tells no one anything the user agent doesn’t already report. A user agent that reports different platforms in different places exposes the one this rule selects. navigator.platform is coarser than the feature, and reports Android and ChromeOS as Linux. The rule also means the feature is wrong exactly when the user agent is already wrong, which authors can’t do anything about, and which users and user agents have chosen.

The web platform already allows this. [HTML] lets navigator.platform return "a string that is commonly returned on another platform" "for privacy and compatibility", and [MEDIAQUERIES-4] records that for the legacy device size features, "for the sake of privacy and security, UAs have been allowed to report inaccurate information". The same section notes that "UA string spoofing does not affect Media Queries, making this a somewhat more robust detection technique". This rule exists so that the platform feature is not that technique.

2.3. Changes

The value is determined when the document is created, and doesn’t change while the document exists.

User agents choose the platform to present when they load a page. Turning "request desktop site" on or off in Chrome requires reloading the page, and WebKit described Safari on iPad as choosing between macOS and iOS when a page is loaded or reloaded, not when its window is resized [WEBKIT-SAFARI-13]. So there is no need for the value to change, and nothing that could link two documents by the moment it changed. Two documents shown one after the other in the same tab can have different values, just as their requests had different User-Agent headers.

2.4. Reduced exposure

In a reduced-exposure context, the feature follows the same rule: it reports the reported platform. A user agent that already normalizes the platform it presents, in that context or generally, gets the same normalization here for free.

There is nothing to take away. A style sheet that reports the value to a server tells it what the server read in the User-Agent header of the request that fetched the style sheet.

3. Privacy considerations

3.1. What the feature reveals

The feature reveals which of seven operating system families the user agent presents itself as. It doesn’t reveal:

  • the version of the operating system, or its build, edition, or distribution;

  • the device model, the manufacturer, the CPU architecture, or the bitness;

  • the browser, its engine, or its version;

  • whether the reported platform is the real one.

3.2. Why it adds nothing

The platform is already available to everyone who can see a request or run script:

  • Every request the document makes carries a User-Agent header that identifies the platform family. Even after Chromium’s User-Agent Reduction, which froze the platform version, the architecture, and the device model, the header still identifies the family: Windows NT 10.0; Win64; x64, Macintosh; Intel Mac OS X 10_15_7, X11; Linux x86_64, X11; CrOS x86_64 14541.0.0, or Linux; Android 10; K [UA-REDUCTION].

  • User agents that implement [UA-CLIENT-HINTS] send Sec-CH-UA-Platform by default on requests to secure origins, because it is in the low-entropy hint table [CLIENT-HINTS-INFRASTRUCTURE]. Safari implements neither the client hint headers nor, for web pages in general, navigator.userAgentData, so its User-Agent header is where it reports the platform.

  • Script can read navigator.userAgent, and navigator.userAgentData.platform where it exists.

Because § 2.2 The reported platform ties the feature to the platform the user agent reports in those, it reaches no context that they don’t. This includes documents where script is disabled, such as messages in an email client: the request that fetched the message, and the request a style sheet would make to report the value, both carry the same User-Agent header.

The rule also means the feature doesn’t make the platform harder to stop exposing. A user agent that stops revealing the platform in its header and client hints, or reveals a different one, changes this feature’s value with it.

3.3. Fingerprinting

The platform family is one of the cheapest parts of the user agent string. Measured across large fingerprint collections, the whole User-Agent string carries about 10 bits of identifying information in Panopticlick’s 2010 data, 9.8 bits in AmIUnique’s 2016 data, and 7.2 bits in the 2018 "Hiding in the Crowd" data set of over two million fingerprints; navigator.platform, on its own, carries 2.3 bits and 1.2 bits in the last two [FINGERPRINT-SURVEY] [HIDING-IN-THE-CROWD]. Those studies don’t measure the operating system family separately, and navigator.platform is only a rough stand-in for it: it reports Android and ChromeOS as Linux, and on Unix-like systems it has at times included the processor architecture. Almost all of the entropy of a user agent string is in versions and device models, which this feature doesn’t report.

The value is also stable, changes only when the user changes platforms, and is the same for large numbers of users. It adds nothing to a fingerprint that the same page’s requests didn’t already carry.

3.4. The closed list

An open list would punish the users of uncommon systems. If the feature had a keyword for every system, a user on one that a thousandth of users run would reveal about 10 bits, while an author who has never seen that system can’t style for it anyway. Every such system reports other, which is also what a user agent reports when it doesn’t want to identify the platform at all.

3.5. User agents that normalize the platform

Firefox’s resist-fingerprinting mode, which Tor Browser uses, normalizes rather than hides. Its user agent string reports all Windows users as Windows NT 10.0, all macOS users as Intel Mac OS X 10.15, all Android users as Android 10, and Linux, the BSDs, and other Unix-like systems all as X11; Linux x86_64. Its source explains why script sees the family: "it is easy to detect the real platform. So there is no benefit for hiding the platform: it only brings breakages, like keyboard shortcuts won’t work in macOS if we spoof it as a Windows platform" [RFP-SERVICE].

The HTTP header used to go further. Until Firefox 136, the mode sent a Windows User-Agent header from macOS and Linux while script reported the real family [MOZ-1840385]. Tor Browser, which inherited this, stopped it in its 14.0 series, having concluded that the practice caused site breakage and gave "only a negligible amount of benefit to the user in terms of additional linkability (i.e. cross-site tracking, fingerprinting) protections, and only then when JavaScript is disabled" [TOR-UA-SPOOFING]. It removed the option entirely in Tor Browser 14.5, released in April 2025 [TOR-43189], and Firefox stopped in version 136. The case both gave up on, a document with script disabled, is the case this feature is most often questioned about, and both now send the normalized family in that case too.

This feature inherits whatever the user agent decides, including a decision to report other everywhere.

3.6. Embedded content

The feature has the same value in cross-origin frames as in the top-level document, because a frame’s own requests carry the same User-Agent header and its script can read the same values.

3.7. Remaining risks

  • Entrenchment. Making platform styling easy makes platform sniffing more common, and sniffing tends to outlive its reason. § 4.1 It is not feature detection and § 5.1 Features for the conventions themselves discuss this.

  • Style-only contexts. A style sheet can report the value without script. It reports a fact the same server already received in a header, but it does so without the page’s script being involved, which a site’s own content security policy might otherwise have limited.

  • Surface. "Already available" is not by itself a reason to expose something again. In the review of User-Agent Client Hints, Henri Sivonen wrote that exposing available information another way "adds more bytes on the wire / more API surface / more complexity to the Web Platform, in which case the harm is the data waste or increased platform complexity and not the identifying bits exposed" [TAG-UA-CH-REVIEW]. That cost applies here. This specification’s answer is that pages already get the same information by parsing the User-Agent string in script, as § 1 Introduction describes, and a single keyword supplied by the user agent is less complexity than a parser in every page.

4. Security considerations

4.1. It is not feature detection

The platform doesn’t say which CSS or JavaScript features work. Sites that decide what to send from the platform break browsers that the site’s author didn’t test, which is the reason user agent strings are full of the names of other browsers. Authors should use @supports, @media capability features such as pointer and hover, and script feature detection, and use this feature only for conventions: what to call a key, which order to put buttons in, which asset to show. [DESIGN-PRINCIPLES] says features should be detectable, and this one deliberately doesn’t help with that.

4.2. Targeting

A page can show different content to users of one platform, such as an attack that tells Windows users to press a key combination that runs a command. Attackers already do this from the server, using the User-Agent header, so the feature adds no reach. What it adds is that the variation can happen entirely in a style sheet, so a service that checks the page by fetching it once, from one platform, sees only one version. Checking services should render pages as more than one platform.

4.3. Not an input to decisions that matter

The user controls the value, through desktop mode, through browser settings, and by choosing a browser that normalizes it. Pages must not use it for licensing, entitlement, fraud scoring, or any security decision.

5. Alternate proposals

5.1. Features for the conventions themselves

Instead of naming the platform, CSS could expose each convention: a feature for how the modifier key is written, one for the order of dialog buttons, one for the direction of the system back gesture. That would say what authors actually need, would survive a platform changing its conventions, and matches how the CSS Working Group has handled other requests, by turning "what device is this" into "what does it do". It was not chosen here because the list of conventions is long and open-ended, and because assets such as store badges and installer formats aren’t conventions the user agent knows about. This is the strongest alternative, and reviewers may prefer it.

5.2. The operating system version

A feature for the version would let a page match the platform’s current design language. It is not proposed: the version is where almost all of the fingerprinting value of a user agent string is, Safari froze the macOS version in its user agent string in 2020 and now reports Intel Mac OS X 10_15_7 permanently, Chromium’s User-Agent Reduction froze it too [UA-REDUCTION], and Sec-CH-UA-Platform-Version is a high-entropy hint that a site has to ask for. Matching a design language is better served by the features that describe it, such as prefers-reduced-transparency and prefers-contrast.

5.3. The device model, architecture, and bitness

A download page would like to offer an Apple Silicon or an Intel build, and Sec-CH-UA-Arch exists for that. These are not proposed: they are high-entropy hints that a site must request, the user agent is told to report them as empty unless a binary download is likely [UA-CLIENT-HINTS], and choosing a download link is something a page can do with script or on the server, where the hint already is.

5.4. The browser or its engine

A feature for the browser brand or engine is not proposed, though the case for it is real. @supports tells a page whether the user agent parses something, not whether it works [CSS-CONDITIONAL-3], so it can’t see an engine that parses a feature and gets it wrong: iOS Safari once resolved svh and dvh to the same length when its tab bar was hidden, which no feature query could detect [WEBKIT-261185].

It is not proposed because the web’s experience with engine detection in CSS is that it can’t be undone, and that the engines it targets end up lying:

  • Content written for WebKit’s prefixed features became so common that the Compatibility Standard now tells every engine to treat -webkit-device-pixel-ratio as an alias of resolution, and defines -webkit-transform-3d for all of them [COMPATIBILITY]. An engine-named media feature has already had to be implemented by the engines it didn’t name.

  • User-Agent Client Hints explains its brand lists with the observation that "History has shown us that there are real incentives for user agents to lie about their branding in order to thread the needle of sites' sniffing scripts", and responds by requiring that "User agents MUST include more than a single value in brands, where one of these values is an arbitrary value" [UA-CLIENT-HINTS].

  • For a smaller browser, as Michael Catanzaro put it, "it is absolutely essential to send a user agent that matches a dominant browser as closely as possible. A small browser cannot be web compatible otherwise" [TAG-UA-FREEZE-REVIEW].

A browser media feature would therefore be answered the same way: the browsers it is meant to identify would report a dominant browser’s value, and it would stop meaning anything. The platform feature accepts that outcome by design, because it follows whatever platform the user agent chooses to present (§ 2.2 The reported platform); it is useful only because most user agents present their real platform family, which is not true of their brand.

Engines have also been closing CSS detection channels rather than opening them: Firefox 58 hid its system-metric media features from web pages [MOZ-1396066], and Firefox never exposed its own platform media feature to them [MOZ-PLATFORM], which is a precedent this specification has to answer (see § 6 Open issues). A page that needs to work around an engine bug should report the bug, and detect its symptom in script where it can.

5.5. A media type

CSS once had media types for device classes, such as @media tv and @media handheld, and they were deprecated because they "have proven insufficient as a way of discriminating between devices with different styling needs" [MEDIAQUERIES-4]: they made one keyword stand for a whole bundle of assumptions. This feature deliberately stands for one thing, the platform’s conventions, and nothing else. Device classes are handled separately by [FORM-FACTOR-MEDIA-QUERY].

6. Open issues

Safari on iPad presents itself as macOS by default, so an iPad in Safari reports macos and gets macOS conventions, including a ⌘ label that matches an attached keyboard but not the on-screen one, and a Mac download where an App Store badge was wanted. Reporting the real platform is not an option: in 2022 WebKit accepted a fix that made the two user agent strings identical, because the one-digit difference "could make it easier for a website to detect whether the visitor is using Mac Safari or is using Mobile Safari, defeating the purpose of desktop mode" [WEBKIT-241322]. Should the specification say anything more to authors, given that the same iPad reports ios in Chrome?

Chrome on Android requests desktop sites by default on premium tablets and reports Linux there [CHROME-DESKTOP-MODE], so those tablets report linux and get a Linux download rather than a Google Play badge. Chromium has features, disabled by default, that report Android or ChromeOS instead on Android devices that run in desktop mode. This specification follows whichever Chromium ships; is that the right outcome for authors?

Should chromeos exist, or should ChromeOS report linux? It has its own conventions, and Sec-CH-UA-Platform distinguishes it, but it is also the only desktop platform here with a single browser. ChromeOS also has a "request tablet site" mode that presents it as Android.

HarmonyOS NEXT’s web engine identifies itself by default in the User-Agent string as OpenHarmony, with no Android token, though some browsers built on it add other system names [HARMONYOS-UA]. It reports "OpenHarmony" as its client hint platform when the app showing the page turns client hints on [ARKWEB-WEBVIEW-API]. Either way it reports other. Should HarmonyOS have a keyword? § 2.1 Adding keywords describes what adding one would mean for existing user agents.

Firefox hid its theme-related media features from web pages in Firefox 58 [MOZ-1396066] (the older bug that asked for it, [MOZ-787521], was closed in Firefox 87). That older bug came from a 2012 report asking Firefox to stop exposing screen and theme information [MOZ-787296], which singled out media queries because they work even with scripting disabled. Does the argument in § 3.2 Why it adds nothing answer that objection for this feature, given that those features exposed settings that the User-Agent header doesn’t carry?

Appendix: Security and privacy questionnaire

This section is non-normative. These are the answers to the questions in [SECURITY-PRIVACY-QUESTIONNAIRE].

What information does this feature expose, and for what purposes?

Which of seven operating system families the user agent presents itself as, so pages can follow that platform’s conventions.

Do features in your specification expose the minimum amount of information necessary?

Yes. A closed list of families, with no version, model, architecture, or browser, and the value must match what the User-Agent header already carries.

Do the features expose personal information, PII, or information derived from either?

No. The platform family suggests little about a person, though it correlates weakly with income and occupation.

How do the features deal with sensitive information?

They expose none beyond what every request already carries.

Does data exposed carry related but distinct information that may not be obvious to users?

Only weakly: on a phone or tablet, a desktop platform can mean that the user or the browser chose a desktop mode.

Do the features introduce state that persists across browsing sessions?

No.

Do the features expose information about the underlying platform to origins?

Yes, its family, to the same extent as the User-Agent header.

Does this specification allow an origin to send data to the underlying platform?

No.

Do features enable access to device sensors?

No.

Do features enable new script execution or loading mechanisms?

No.

Do features allow an origin to access other devices?

No.

Do features allow an origin some measure of control over a user agent’s native UI?

No.

What temporary identifiers do the features create or expose to the web?

None. The value doesn’t change while a document exists.

How does this specification distinguish between behavior in first-party and third-party contexts?

It doesn’t, because a cross-origin frame’s own requests carry the same header.

How do the features work in the context of a browser’s Private Browsing or Incognito mode?

The same as the User-Agent header does in that mode. A user agent that normalizes the platform there reports the normalized value here.

Does this specification have both "Security Considerations" and "Privacy Considerations" sections?

Yes.

Do features enable origins to downgrade default security protections?

No.

What happens when a document that uses your feature is kept alive in BFCache?

It keeps the value it was created with, as its User-Agent header would.

What happens when a document that uses your feature gets disconnected?

Nothing is kept.

Does your spec define when and how new kinds of errors should be raised?

No.

Does your feature allow sites to learn about the user’s use of assistive technology?

No.

What should this questionnaire have asked?

Whether a feature encourages a practice, such as user-agent sniffing, whose cost falls on browsers and users that the author never tested.

Conformance

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with class="note", like this:

Note, this is an informative note.

Issues Index

Safari on iPad presents itself as macOS by default, so an iPad in Safari reports macos and gets macOS conventions, including a ⌘ label that matches an attached keyboard but not the on-screen one, and a Mac download where an App Store badge was wanted. Reporting the real platform is not an option: in 2022 WebKit accepted a fix that made the two user agent strings identical, because the one-digit difference "could make it easier for a website to detect whether the visitor is using Mac Safari or is using Mobile Safari, defeating the purpose of desktop mode" [WEBKIT-241322]. Should the specification say anything more to authors, given that the same iPad reports ios in Chrome? ↵
Chrome on Android requests desktop sites by default on premium tablets and reports Linux there [CHROME-DESKTOP-MODE], so those tablets report linux and get a Linux download rather than a Google Play badge. Chromium has features, disabled by default, that report Android or ChromeOS instead on Android devices that run in desktop mode. This specification follows whichever Chromium ships; is that the right outcome for authors? ↵
Should chromeos exist, or should ChromeOS report linux? It has its own conventions, and Sec-CH-UA-Platform distinguishes it, but it is also the only desktop platform here with a single browser. ChromeOS also has a "request tablet site" mode that presents it as Android. ↵
HarmonyOS NEXT’s web engine identifies itself by default in the User-Agent string as OpenHarmony, with no Android token, though some browsers built on it add other system names [HARMONYOS-UA]. It reports "OpenHarmony" as its client hint platform when the app showing the page turns client hints on [ARKWEB-WEBVIEW-API]. Either way it reports other. Should HarmonyOS have a keyword? § 2.1 Adding keywords describes what adding one would mean for existing user agents. ↵
Firefox hid its theme-related media features from web pages in Firefox 58 [MOZ-1396066] (the older bug that asked for it, [MOZ-787521], was closed in Firefox 87). That older bug came from a 2012 report asking Firefox to stop exposing screen and theme information [MOZ-787296], which singled out media queries because they work even with scripting disabled. Does the argument in § 3.2 Why it adds nothing answer that objection for this feature, given that those features exposed settings that the User-Agent header doesn’t carry? ↵
