Abstract

This specification adds media features and functions that test the current date and time: date, time, weekday, month, day, moon-phase, and season, plus the holiday() and calendar() functions. Dates and times are written as the ISO 8601 strings that Temporal parses, such as "2026-09-09", "--12-25", and "18:00", so a style sheet can turn on a sale banner for one week, a winter theme every December, or a launch button at one moment worldwide, without script.

1. Introduction

This section is non-normative.

Sites change with the calendar. A store shows a sale banner for one week, a news site switches to a darker look in the evening, a game adds snow in December, and a product page reveals its "Buy now" button at the moment of launch. Today each of these needs script that reads the clock, compares dates, and toggles a class, and then has to run again when the date changes while the page is open.

This specification lets a style sheet ask about the date directly, the same way it asks about the width of the viewport. Dates and times are written as ISO 8601 strings, in exactly the formats that Temporal [TEMPORAL] parses, and they compare the way Temporal compares them.

/* A sale banner from September 9 through September 15, 2026 */
@media ("2026-09-09" <= date <= "2026-09-15") {
  .sale-banner { display: block; }
}

/* Snow every year from December 20 through January 5 */
@media (date >= "--12-20"), (date <= "--01-05") {
  body { background-image: url(snow.svg); }
}

/* Warmer colors from 6pm local time */
@media (time >= "18:00") {
  :root { --accent: orange; }
}

/* "Buy now" appears at 9:00 in New York, the same moment everywhere */
@media (date >= "2026-11-27T09:00[America/New_York]") {
  .buy-now { display: inline-block; }
}

/* US Thanksgiving, and Passover in the Hebrew calendar */
@media holiday(us, thanksgiving) { … }
@media calendar(hebrew, (month: M07) and (15 <= day <= 22)) { … }

/* Full moon, and winter in whichever hemisphere the user is in */
@media (moon-phase: full-moon) { … }
@media (season: winter) { … }

Because these are media queries, they also work in HTML’s media attributes and in matchMedia(), and they update on their own when the date changes.

<picture>
  <source media='(date = "--12-25")' srcset="hero-christmas.jpg">
  <img src="hero.jpg" alt="">
</picture>

CSS strings can use single or double quotes, so a query inside an HTML attribute uses whichever quote the attribute doesn’t.

2. Syntax

This specification makes two changes to the media query grammar in [MEDIAQUERIES-5].

  1. <mf-value> gains a <string> alternative, so a media feature can be compared with a string:

    <mf-value> = <number> | <dimension> | <ident> | <ratio> | <string>

    The media features in [MEDIAQUERIES-5] don’t accept strings, so this changes nothing for them.

  2. <media-in-parens> gains the holiday() and calendar() functions:

    <media-in-parens> = ( <media-condition> ) | ( <media-feature> )
                    | <holiday()> | <calendar()> | <general-enclosed>

    As before, the <general-enclosed> branch is chosen only if the input matches none of the others.

A user agent that doesn’t implement this specification parses every query in it as <general-enclosed>, or as an unknown <media-feature>. Both evaluate to "unknown", which makes the media query false. Styles meant for a date are never applied early by an older browser; they are not applied at all.

3. The current date and time

The current instant is SystemUTCEpochNanoseconds(), rounded down to a whole second (a multiple of 109 nanoseconds).

The current time zone is SystemTimeZoneIdentifier().

The current date-time is the ISO Date-Time Record returned by GetISODateTimeFor(current time zone, current instant). Its [[ISODate]] field is the current date, and its [[Time]] field is the current time.

These are the values that Temporal.Now.zonedDateTimeISO() returns in script, except for the rounding. A document’s styles and its scripts agree about what day it is.

When the user agent evaluates media queries for a document, it uses one current instant for all of them, so two queries about the same moment never disagree.

The media features and functions in this specification change value as time passes, and when the current time zone or the system clock changes. When that changes the result of a media query, the user agent must respond as it does when any other media feature changes: it restyles the document and fires change events at the affected MediaQueryList objects. It should do so within one second.

Implementations don’t need to poll. From the queries in use, a user agent can work out the next instant at which any result can change, such as a boundary written in a query or the next local midnight, and wait until then.

4. Date and time strings

4.1. Date strings

A <date-string> is a <string> for which parse a date string doesn’t return failure.

To parse a date string s, run these steps. If any operation they call throws an exception, return failure.

  1. If ParseText(s, TemporalDateTimeString[+Zoned]) is a Parse Node, the string names a time zone. Return an instant value: the [[EpochNanoseconds]] of ToTemporalZonedDateTime(s).

  2. If ParseText(s, TemporalInstantString) is a Parse Node, the string has a UTC offset. Return an instant value: the [[EpochNanoseconds]] of ToTemporalInstant(s).

  3. If ParseText(s, TemporalDateTimeString[~Zoned]) is a Parse Node:

    1. Let result be ParseISODateTime(s, « TemporalDateTimeString[~Zoned] »).

    2. If result.[[Calendar]] is not empty, perform CanonicalizeCalendar(result.[[Calendar]]).

    3. Let date be the ISO Date Record with [[Year]] result.[[Year]], [[Month]] result.[[Month]], and [[Day]] result.[[Day]].

    4. If ISODateWithinLimits(date) is false, return failure.

    5. If result.[[Time]] is start-of-day, the string has no time. Return a date value: date.

    6. Let dateTime be CombineISODateAndTimeRecord(date, result.[[Time]]).

    7. If ISODateTimeWithinLimits(dateTime) is false, return failure.

    8. Return a date-time value: dateTime.

  4. If ParseText(s, AnnotatedMonthDay) is a Parse Node:

    1. Let result be ParseISODateTime(s, « TemporalMonthDayString »).

    2. Return a month-day value: the pair (result.[[Month]], result.[[Day]]).

  5. Return failure.

A calendar annotation such as [u-ca=hebrew] is accepted, as Temporal accepts it, but it doesn’t change the date: the fields of the string are always ISO 8601 fields. To match dates in another calendar, use calendar().

To compare the current date with a parsed date string v:

If v is an instant value

Return CompareEpochNanoseconds(current instant, v).

If v is a date-time value

Return CompareISODateTime(current date-time, v).

If v is a date value

Return CompareISODate(current date, v).

If v is a month-day value (month, day)

Return CompareISODate(a, b), where a is the ISO Date Record for year 1972 with the current date’s month and day, and b is the one for year 1972 with month and day.

The result is -1 if the current date comes first, 0 if they are equal, and 1 if v comes first.

1972 is the reference year that Temporal uses for PlainMonthDay. It is a leap year, so "--02-29" is a valid month-day. In other years no date is equal to it, and March 1 is after it.
String Kind Meaning
"2026-09-09" date September 9, 2026, in the user’s time zone
"20260909" date The same date, in ISO 8601 basic format
"2026-11-27T09:00" date-time 9:00 on November 27, 2026, in the user’s time zone
"2026-11-27T09:00[America/New_York]" instant 9:00 on that day in New York, one moment for every user
"2026-11-27T14:00Z" instant The same moment, written in UTC
"2026-11-27[America/New_York]" instant The start of that day in New York
"--12-25" or "12-25" month-day December 25 of every year

4.2. Time strings

A <time-string> is a <string> for which parse a time string doesn’t return failure.

To parse a time string s:

  1. If s doesn’t start with "T" or "t", set s to the concatenation of "T" and s.

  2. If ParseText(s, TimeDesignator Time) is not a Parse Node, return failure.

  3. Return the [[Time]] of ToTemporalTime(s). If that throws, return failure.

Adding the "T" prevents a basic-format time such as "1225" from being read as a month and day, which is how Temporal resolves the same ambiguity.

5. Media features

All of these features have a value at all times, so in a boolean context they are always true. Range features also accept the min- and max- prefixes, as [MEDIAQUERIES-5] defines for every range feature.

5.1. The date feature

Name: date
For: @media
Value: <date-string>
Type: range

The date media feature is the current date and time. Compared with a <date-string> v, the feature is less than, equal to, or greater than v when the result of comparing the current date with v is -1, 0, or 1.

Each comparison in a query parses its own string, so a range can mix kinds: ("2026-09-09" <= date < "2026-09-15T12:00") starts at the beginning of September 9 and ends at noon on September 15.

A range of month-days doesn’t wrap around the end of the year, because ("--12-20" <= date <= "--01-05") means (date >= "--12-20") and (date <= "--01-05"), which no date satisfies. Join the two halves with a comma or or instead: 
@media (date >= "--12-20") or (date <= "--01-05") { … }

5.2. The time feature

Name: time
For: @media
Value: <time-string>
Type: range

The time media feature is the current time. Compared with a <time-string>, whose parsed value is t, the feature is less than, equal to, or greater than it when CompareTimeRecord(current time, t) is -1, 0, or 1.

/* From 10pm to 6am */
@media (time >= "22:00") or (time < "06:00") { … }

5.3. The weekday feature

Name: weekday
For: @media
Value: monday | tuesday | wednesday | thursday | friday | saturday | sunday
Type: range

The weekday media feature is the day of the week of the current date. The keywords stand for the numbers 1 (monday) through 7 (sunday), the numbering of ISODayOfWeek, and compare as those numbers. The value is ISODayOfWeek(current date).

@media (weekday >= saturday) { .weekend-hours { display: block; } }

5.4. The month feature

Name: month
For: @media
Value: <integer [1,99]> | <month-code>
Type: range

A <month-code> is an <ident> that, converted to ASCII uppercase, is matched by the MonthCode production of [TEMPORAL], such as M01 or M05L. An <integer> n is equivalent to the month code CreateMonthCode(n, false), so 12 means M12.

The month media feature is the [[MonthCode]] of CalendarISOToDate(date calendar, current date). Month codes compare by code unit order, which [TEMPORAL] defines to be the order of the months in a year, including leap months.

5.5. The day feature

Name: day
For: @media
Value: <integer [1,∞]>
Type: range

The day media feature is the [[Day]] of CalendarISOToDate(date calendar, current date): the day of the month.

month, day, and weekday together describe any "nth weekday of the month" rule, because the fourth Thursday of a month always falls on day 22 to 28, and the last Monday of May on day 25 to 31: 
@media (month: 11) and (weekday: thursday) and (22 <= day <= 28) { /* US Thanksgiving */ }
@media (month: 5) and (weekday: monday) and (day >= 25) { /* US Memorial Day */ }

5.6. The moon-phase feature

Name: moon-phase
For: @media
Value: new-moon | waxing-crescent | first-quarter | waxing-gibbous | full-moon | waning-gibbous | last-quarter | waning-crescent
Type: discrete

The principal phases of the Moon are the instants at which the Moon’s geocentric apparent ecliptic longitude exceeds the Sun’s by 0° (new-moon), 90° (first-quarter), 180° (full-moon), and 270° (last-quarter). The date of a principal phase is the [[ISODate]] of GetISODateTimeFor(current time zone, the phase’s instant).

The moon-phase media feature is:

  • The principal phase whose date is the current date, if there is one.

  • Otherwise, the phase after the most recent of the principal phases: waxing-crescent after new-moon, waxing-gibbous after first-quarter, waning-gibbous after full-moon, and waning-crescent after last-quarter.

User agents must place the instants of the principal phases within one minute of their true times.

The method in chapter 49 of [MEEUS] is accurate enough. Principal phases are about seven days apart, so no date has two of them. Because the date depends on the time zone, users in different time zones can see a full moon on different dates.

5.7. The season feature

Name: season
For: @media
Value: spring | summer | autumn | winter
Type: discrete

The astronomical seasons are bounded by the March equinox, June solstice, September equinox, and December solstice: the instants at which the Sun’s geocentric apparent ecliptic longitude is 0°, 90°, 180°, and 270°. The date of each is the [[ISODate]] of GetISODateTimeFor(current time zone, its instant) in the year of the current date.

The hemisphere is southern if the current time zone is a named time zone whose location in the Time Zone Database [TZDB] has a negative latitude, and northern otherwise. Offset time zones and zones with no location, such as "UTC", are northern. User agents use the entry for the time zone’s own identifier where the database lists one, and otherwise the entry for the zone it links to.

The season media feature is found from the current date d:

When d is Northern Southern
on or after the date of the March equinox and before the date of the June solstice spring autumn
on or after the date of the June solstice and before the date of the September equinox summer winter
on or after the date of the September equinox and before the date of the December solstice autumn spring
any other date winter summer

User agents must place the equinoxes and solstices within one minute of their true times.

The method in chapter 27 of [MEEUS] is accurate enough for dates near the present. The hemisphere comes from the time zone, which script can already read, rather than from the user’s location. Near the equator the astronomical seasons don’t match the local climate, and authors should keep that in mind for audiences there.

6. Functions

6.1. The calendar() function

<calendar()> = calendar( <ident> , <media-condition> )

The calendar() function evaluates a media condition in another calendar.

Every media condition is evaluated with a date calendar, which is "iso8601" unless calendar() says otherwise. The date calendar decides what month and day mean. It doesn’t affect date, time, or weekday, which are the same in every calendar.

To evaluate calendar(name, condition):

  1. Let calendar be CanonicalizeCalendar(name). If that throws, because the user agent doesn’t support a calendar of that calendar type, the result is "unknown".

  2. The result is the result of evaluating condition with calendar as the date calendar.

The calendar types are the ones Intl.DateTimeFormat supports, such as hebrew, chinese, islamic-umalqura, persian, and ethiopic.

/* Lunar New Year through the Lantern Festival */
@media calendar(chinese, (month: M01) and (day <= 15)) { … }

/* Purim: 14 Adar, which is Adar II in a Hebrew leap year */
@media calendar(hebrew, (month: M06) and (day = 14)) { … }

6.2. The holiday() function

<holiday()> = holiday( [ <ident> , ]? <ident> )

The holiday() function tests whether the current date is a holiday. Its last argument names the holiday. The optional first argument is a region: two ASCII letters, an ISO 3166-1 alpha-2 code as used in Unicode region subtags, such as us or il. The author chooses the region; the user’s own region plays no part.

To evaluate holiday(region, name), with region possibly omitted:

  1. If region is present and isn’t two ASCII letters, the result is "unknown".

  2. Let entry be the entry of the § 6.3 Holiday registry whose name matches name and whose region matches region, ignoring ASCII case.

  3. If there is no such entry, let entry be the entry whose name matches name and that has no region.

  4. If there is still no entry, the result is "unknown".

  5. The result is true if the current date is a date of entry, and false otherwise.

The dates of an entry are the dates on which its rule’s media condition is true, evaluated with "iso8601" as the date calendar, or the dates its rule describes in words. If an entry’s rule uses a calendar that the user agent doesn’t support, the result is "unknown".

@media holiday(us, thanksgiving) { … }  /* fourth Thursday of November */
@media holiday(ca, thanksgiving) { … }  /* second Monday of October */
@media holiday(us, christmas) { … }     /* no US entry, so the regionless one */
@media holiday(il, passover) { … }      /* 7 days in Israel, instead of 8 */

The Gregorian Easter of year Y is found with integer division and a non-negative remainder:

  1. Let a be Y mod 19, b be Y ÷ 100, and c be Y mod 100.

  2. Let d be b ÷ 4, e be b mod 4, f be (b + 8) ÷ 25, and g be (b − f + 1) ÷ 3.

  3. Let h be (19a + b − d − g + 15) mod 30.

  4. Let i be c ÷ 4, and k be c mod 4.

  5. Let l be (32 + 2e + 2i − h − k) mod 7.

  6. Let m be (a + 11h + 22l) ÷ 451.

  7. Let n be h + l − 7m + 114.

  8. Return the ISO date in year Y, month n ÷ 31, day (n mod 31) + 1.

The Orthodox Easter of year Y is found the same way:

  1. Let a be Y mod 4, b be Y mod 7, and c be Y mod 19.

  2. Let d be (19c + 15) mod 30.

  3. Let e be (2a + 4b − d + 34) mod 7.

  4. Let n be d + e + 114.

  5. Let julian be the date in year Y, month n ÷ 31, day (n mod 31) + 1, in the Julian calendar.

  6. Return the ISO date (Y ÷ 100) − (Y ÷ 400) − 2 days after the ISO date with the same fields as julian.

These are the algorithms in chapter 8 of [MEEUS]. Every other rule in the registry is a media query that authors could write themselves; the registry gives them names and keeps regional differences, like the length of Passover, in one place.

New entries are added through the specification’s issue tracker. An entry can only be added if its dates can be calculated. Holidays whose dates depend on observation, or on calendars that Intl.DateTimeFormat doesn’t support, aren’t eligible; see § 10 Open issues.

7. Privacy considerations

  • The current date and time and the user’s time zone are already available to script, through Date, Temporal, and Intl. These features make them available to style sheets, including in contexts where script doesn’t run, such as HTML email or pages with script blocked. A style sheet can report them to a server by loading different resources under different queries. User agents that block script for privacy should consider the same treatment for these features, such as evaluating them in the "UTC" time zone.

  • The current instant is rounded down to a second, so queries can’t measure the user’s clock more finely than that.

  • The hemisphere for season comes from the time zone, not from the user’s location.

  • The region in holiday() is chosen by the author. Nothing in this specification reveals the user’s region or locale.

8. Security considerations

  • These features show and hide content; they don’t protect it. Content hidden until a date is in the style sheet and the document already, and users can change their clocks. Embargoed content must stay on the server until its release.

  • Nothing in this specification fetches resources or runs script.

9. Alternate proposals

9.1. ISO 8601 basic format as numbers

ISO 8601’s basic format writes dates and times without separators, and those parse as CSS numbers: (20260909 <= date <= 20260915), (date = 1225), (time >= 1800). That needs no grammar change. It was not chosen because:

  • A number has no time zone or UTC offset, so "9:00 in New York" can’t be written.

  • A specific moment takes several conditions: (date > 20261127), ((date = 20261127) and (time >= 900)).

  • Leading zeros vanish, so January 5 is 105, and the number of digits decides whether a number is a date or a month-day.

9.2. Features instead of functions

Holidays and calendars could be media features with no grammar change: (holiday: us-thanksgiving), and per-calendar features such as (hebrew-month: M07) and (hebrew-day >= 15). It was not chosen because a date can be several holidays at once, which no other media feature allows, and because a pair of features for every calendar multiplies the feature names.

9.3. A locale in holiday()

The first argument could be a locale, such as en-us. Holidays depend on the region, not the language, so only the region is used.

10. Open issues

Islamic holidays, such as Eid al-Fitr and the start of Ramadan, begin when the new crescent moon is sighted, which no algorithm predicts. Authors who accept a tabular approximation can use calendar(islamic-umalqura, (month: M09)). Should the registry include such entries with that caveat?

Diwali, Holi, Vesak, and other holidays of Hindu and Buddhist lunisolar calendars can’t be listed, because CLDR and Intl.DateTimeFormat don’t support those calendars.

Many events are relative to a holiday: Black Friday is the day after US Thanksgiving, and a sale might run for the week before Christmas. Should holiday() accept a range of days before and after?

Some countries use meteorological seasons, which start on the first of March, June, September, and December. Should season offer them?

Which days are the weekend depends on the region: Saturday and Sunday in most of the world, Friday and Saturday in others. Should there be a way to test for the weekend, as Intl.Locale.prototype.getWeekInfo() reports it?

Conformance

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with class="note", like this:

Note, this is an informative note.

Issues Index

Islamic holidays, such as Eid al-Fitr and the start of Ramadan, begin when the new crescent moon is sighted, which no algorithm predicts. Authors who accept a tabular approximation can use calendar(islamic-umalqura, (month: M09)). Should the registry include such entries with that caveat? ↵
Diwali, Holi, Vesak, and other holidays of Hindu and Buddhist lunisolar calendars can’t be listed, because CLDR and Intl.DateTimeFormat don’t support those calendars. ↵
Many events are relative to a holiday: Black Friday is the day after US Thanksgiving, and a sale might run for the week before Christmas. Should holiday() accept a range of days before and after? ↵
Some countries use meteorological seasons, which start on the first of March, June, September, and December. Should season offer them? ↵
Which days are the weekend depends on the region: Saturday and Sunday in most of the world, Friday and Saturday in others. Should there be a way to test for the weekend, as Intl.Locale.prototype.getWeekInfo() reports it? ↵
